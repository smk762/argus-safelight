# CLAUDE.md — argus-safelight

Guidance for AI agents working in this repo. Human-facing usage lives in [README.md](README.md); the design and its acceptance list live in [spec.md](spec.md). This file is the orientation an agent needs to change code safely.

## What this is

The standalone **demo UI for argus-darkroom**: compose a prompt, see the pre-flight verdict, generate over SSE, see what every guard said about the output, browse the history. It is a client. Darkroom decides everything; safelight shows the record and decides nothing.

- `web/`: Next.js 16 App Router, React 19, Tailwind v4, vitest 4. Two builds from one tree. **Live** (default): a server, generation is live, pages call darkroom directly from the browser at `NEXT_PUBLIC_DARKROOM_URL` (default `http://localhost:8106`, baked in at build). **Static demo** (`SAFELIGHT_STATIC=1`, `make pages`): a pure static export that replays the recorded tape in `web/public/data-tape` and never calls darkroom (see "Static demo" below).
- `scripts/record_tape.py`: writes the tape (`sample` from `fixture/`, `live` from a darkroom and `docs/demo-takes.json`). `docs/demo-recording.md` is the recording plan; nothing is recorded without the maintainer's approval.
- `scripts/mock_darkroom.mjs`: a zero-dependency Node mock of darkroom's API that serves `fixture/` and generates new records with the verdict chosen by prompt markers (`[flag]`, `[illegal]`, `[exposed]`, … listed at the top of the file and in the README).
- `scripts/make_fixture.py`: draws `fixture/` (PEP 723 script, `uv run`). `fixture/` is committed; the web tests read it, so it doubles as a contract test between the mock and the UI. It records the darkroom version from the sync record (`fixture/darkroom.json`, every `darkroom_version`).
- `web/schema/pins.json`: the **sync record** for argus-darkroom at its `dev` HEAD (commit, version, a sha256 per imported file). `web/scripts/darkroom-sync.mjs` pulls (`--pull`, network, through `scripts/opsec.mjs`), checks (`--check`, offline, in `make lint` and CI) and generates `src/lib/generated/darkroom.ts`. `web/content/darkroom/` holds darkroom's README and spec.md verbatim; `/docs` renders them. `.github/workflows/darkroom-drift.yml` opens the sync PR daily.

There is no host Node here; the Makefile runs npm in `node:22-bookworm-slim` via Docker when `npm` is missing. Use `docker compose`, never `docker-compose`.

## Modern Web Guidance

Frontend work here uses the [Modern Web Guidance](https://developer.chrome.com/docs/modern-web-guidance) skill (`/modern-web-guidance`). It is installed per user, not committed, because it fetches its guides with `npx` at query time: `/plugin marketplace add GoogleChrome/modern-web-guidance` then `/plugin install modern-web-guidance@googlechrome` in Claude Code, or `npx modern-web-guidance@latest install` for other agents. Search it before writing dialog, popover, form, image or CSP code; `npx -y modern-web-guidance@latest legacy-scan web/src --json` is the modernization pass (clean as of issue #23).

House exceptions to its advice, with the reason:

- **Browser support:** Baseline widely available, plus newly available features that degrade on their own (`closedby="any"` on the purge dialog keeps an `onClick` backdrop fallback). No polyfills.
- **Shield detail stays `popover="manual"`** with `placeBeside` and React state, not `popover="hint"` + `interestfor` + anchor positioning: none of those three is in every current engine, and the guide's way needs a polyfill for each.
- **The status card and `Tip` stay CSS-revealed** (`group-hover`/`group-focus-within`) for the same reason, with `useEscapeDismiss` covering WCAG 1.4.13's "dismissible".
- **History thumbnails load darkroom's full image**, lazily. Darkroom serves no thumbnail size; that is a darkroom change, not a client one.

## Static demo

- **One flag, inlined.** `staticDemo()` (`lib/demo.ts`) reads `NEXT_PUBLIC_SAFELIGHT_STATIC` literally, so each build carries one branch. `api.ts` sends every read to `lib/staticApi.ts` (the tape) in the static build and rejects every write with `NotInDemo`. Components hide write controls with `staticDemo()` rather than badging them "not in this demo".
- **Build-specific files** carry the build's extension, picked by `pageExtensions` in `next.config.ts`: `src/proxy.live.ts`, `app/record/[id]/page.live.tsx` and `page.static.tsx` (generateStaticParams from the tape). The live layout reads the nonce; the static one must not call `headers()`.
- **CSP:** `web/scripts/csp.mjs` adds a hash CSP `<meta>`, a Trusted Types `default` policy and the `dh-theme.js` tag to every exported page; the policy names `'self'` only. Never add an inline script or a server-rendered `style` attribute.
- **The tape decides what can be fetched.** `tape.files` has entries for passed and review records only; `imageUrl`/`thumbUrl`/`veilUrl` return `""` for anything else. A veiled frame (`tape.veiled`) renders the veil and requests neither its thumbnail nor its image until Reveal. A blocked record (critical, an illegal cell, or minor-exposed) is withheld by `record_tape.py` before the tape is written; the page never sees its words. `check-static.mjs` and `tape.test.ts` enforce all of it; `demo-e2e.mjs` checks the requests in a browser.
- **Content rules for any recording** are in `docs/demo-recording.md`: synthetic adults, catalogue-level at most, and never a generation of anything a guard should block. Illegal and minor-exposed outcomes are hand-written fixture records (`--illustrative`), labelled Sample data.
- **Dragonhound shared layer:** `web/vendor/dh` is vendored (dh-shared 1.2.5) and never edited; `make shared-check` and the `dh-shared` CI job pin it. `public/dh-theme.js` is a copy (`shared.test.ts`). The strip renders in the static build only, with `data-dh-site="safelight"`.

## Conventions & gotchas

- **The browser decides nothing.** Outcome, cell states, blur, the fired rule: all from the record. Do not reclassify rules, compare scores to thresholds, or infer a policy's mode from its name (`/policies` says `mode`). The blur threshold in the form changes the request, not the display.
- **Never an `<img>` for deleted, omitted, refused or failed.** `hasImage()` is the gate; `ResultView.test.tsx` asserts no `img`/`picture`/`canvas`/`video` in the DOM for those outcomes. Images load by id (`imageUrl(id)` → `GET /image/{id}`), never by `image.path`.
- **Deleted must not read like omitted.** Deleted is red, "destroyed", names the rule, policy and scan context. Omitted is plain, "withheld", names NudeNet's score or its silence. Keep the wording in `outcome.ts`.
- **Age wording** is in `age.ts` only: "MiVOLO estimate: N" with the hover text, never a bare age or an "Age" field. Minor-exposed deletions are phrased as "a MiVOLO age estimate under 18 together with NudeNet exposure".
- **Shields carry a mark and a label** (`shieldMark`, `shieldLabel`); colour is never the only signal. The enforcing policy is first in every grid and labelled.
- **A shield's detail is a native popover** (`popover="manual"`, placed by `placeBeside`). It has to be in the top layer: the grids scroll and the pre-flight shields sit in the compose dialog, so `absolute` and `z-index` get clipped or hidden.
- **Modals are native `<dialog>` opened with `showModal()`** (`ComposeDialog`, `PolicyDialog`, `PurgeDialog`): the browser gives the inert page, focus containment, Escape and the top layer, so no `role="dialog"`, `aria-modal`, focus trap or Escape listener. Name each with `aria-labelledby`. Close with `dialog.close()` and react in `onClose`, so the focus returns to the opener; unmounting an open dialog skips that. jsdom has no `showModal`; the component tests stub it.
- **Hover and focus content closes on Escape** without the pointer or focus moving (WCAG 1.4.13): `useEscapeDismiss` for the CSS-revealed `Tip` and status card, a document listener in `ShieldCell`, which also `preventDefault`s so the same Escape does not close the compose dialog behind it.
- **CSP:** `src/proxy.live.ts` sets a nonce CSP on every page (`lib/csp.ts`): nonced scripts with `'strict-dynamic'`, nonced styles, and darkroom's origin for `connect-src`/`img-src`, resolved from the request's Host with `darkroomUrl()`. The layout puts the nonce on the `dh-theme.js` tag; any new `<script>` needs it too, and a server-rendered `style` attribute is blocked in production (set styles from the client, as `LiveView` and `placeBeside` do). Development adds `'unsafe-eval'` and `'unsafe-inline'` styles for `next dev` only. Reading the nonce makes every route dynamic, which is expected.
- **Server and browser must render the same text.** Anything that depends on `window` (the darkroom URL the page calls, the theme) goes through `useSyncExternalStore` with a server snapshot, or the page logs a hydration error on any host but localhost.
- **Disagreement needs two verdicts.** `rowDisagrees` is false while a cell is pending and when either cell is `unchecked`; the ≠ badge and the "Prompt changed the verdict" filter both use it. `promptTurned` (dashed outline) is safe → flagged/illegal only.
- **The record types are generated, never edited.** `make sync` pulls darkroom's schema and regenerates `generated/darkroom.ts`; then fix what typecheck reports, update `scripts/make_fixture.py` and the mock, and `make fixture`. `wire.test.ts` validates every fixture record against the schema with every field required and nothing extra, as darkroom serializes it (its schema is Pydantic's validation view, where a defaulted field is optional; the generator makes them all required). Darkroom re-validates a stored record on read, so an older record still arrives with every field. Shapes outside the schema (`Health`, `Policies`, `Models`, `GenerateRequest`, `Preflight`, the events) stay hand-written in `types.ts`. Check a change against the real server with darkroom's `make demo` (same shapes, fake backends), not only the mock.
- **Docs, wire types and fixture move together.** Never edit `web/content/darkroom/`, `web/schema/` or `fixture/darkroom.json` by hand: `make lint` checks each against `pins.json`. The opsec gate refuses and never redacts; fix a refused doc in darkroom. Every in-context help link is in `docsLinks.ts`, and `docsLinks.test.tsx` renders the imported pages and fails when a target anchor is gone, so a heading darkroom renames breaks the sync PR, not production. Markdown renders as React elements: no `rehype-raw`, no `dangerouslySetInnerHTML`, no `style` (GFM's table alignment is dropped). A docs link inside the compose dialog opens a new tab (`DocsLink newTab`), so the form is not left mid-thought.
- **`outcome_reason` is a joined list.** `policy:letter` codes and words, comma-separated (`adult-granular:A, minor-exposed`). Read it with `reasonParts`, and never compare the whole string to a word. `firedCell` matches a code on its policy as well as its letter, because letters mean different things per policy.
- **A record refused in pre-flight resolved nothing.** `checkpoint`, `vae`, `workflow_sha256`, `workflow` and `engine_version` are null, `loras` is empty, and `seed` and `sampling` are only what the request sent. `fromRecord` keeps the form's own values for those.
- **The form offers only what a workflow renders.** Darkroom picks a template per generation by the checkpoint's `family` and the LoRA count, and 400s a request that sets a value the template has no slot for. `workflows.ts` reads the same thing from `/models` (`workflowFor` mirrors darkroom's `WorkflowSet.select`); it does not decide anything darkroom would not. So: a checkpoint with empty `lora_counts` is listed but disabled, LoRAs stop where the family's counts stop, Generate is blocked with darkroom's reason, and `toRequest` sends `guidance` only with a `$guidance` slot (Flux requires it), no negative prompt without `$negative` (the form keeps it for the next family that takes one), and clip skip above 2 only with `$clip_skip`. The form has no VAE picker; no shipped template has `$vae`. **Pre-flight does not check workflows** (darkroom's doesn't, nor does the mock), so Check stays enabled. Per-family sampling (`familySampling`) is a starting point applied when the family changes, never a constraint. After a workflow change, run the contract test against darkroom's demo (never a GPU server: each accepted case generates): `DARKROOM_CONTRACT_URL=http://127.0.0.1:8116 npx vitest run src/lib/workflows.contract.test.ts`; it covers every mode, with a generated PNG input and mask, and the masks darkroom refuses. The demo needs `--cors-origin` only for a browser, not for this. Darkroom's demo cannot finish an image-to-image render yet (its fake ComfyUI reads the size from an empty latent), so such a run ends `failed` there; the input scan and the record shapes are still darkroom's.
- **Input images never leave memory, except in the generate request.** `ComposeState.initImage`/`mask` hold base64 and a `data:` URL; nothing goes to `localStorage`/`sessionStorage` (a draft may keep `denoise`). `POST /preflight` gets `withoutPixels(request)`, since darkroom's pre-flight judges the text alone, and the live state and the pre-flight comparison key (`preflightKey`) never hold pixels either. The client checks mirror darkroom's (`images.load_input`/`load_mask`): magic bytes, 16 MiB, 4096 px, the mask at the input's upright size (the browser decodes upright, as darkroom's EXIF transpose does), and a mask with nothing at or above grey 128 is "masks nothing". Darkroom still checks everything.
- **Modes come from `/models`, never a fallback.** An input selects image-to-image, a mask inpainting; `workflowFor` matches `mode` (absent means txt2img) and `modeCounts` reads `lora_counts`, `img2img_lora_counts` or `inpaint_lora_counts`. Darkroom never renders an input as text-to-image or drops a mask, so neither does the form: Generate is blocked with the reason.
- **An input refusal is read from `guard.input`, not the reason's wording.** `inputRefused(record)` is `outcome === "refused"` with `guard.input.outcome !== "passed"`; `reasonParts` drops the `input image: ` prefix, and `inputRefusalSummary` reads each reason against the input's scan. Only a passed input goes on: a review-level input refuses. A record keeps no input pixels, so the record view shows hashes, size, denoise and the mask's share, and says so; `fromRecord` sets `recordInput` and Generate waits until the image is chosen again or the user goes on from text. The input's age estimate is MiVOLO wording via `AgeEstimate`, as everywhere.
- **Trigger words are per LoRA and per request.** They are in the request's `loras[].trigger_words` and in the record's `request.loras[].trigger_words`; darkroom appends them to the final prompt. `fromRecord` refills them. Never append them in the client.
- **Hooks lint is strict** (`react-hooks/set-state-in-effect`, `react-hooks/refs`): no synchronous `setState` inside effects. Use `useLoad` for keyed fetches, `useSyncExternalStore` for browser state (see `theme.ts`), and derive loading from keys rather than resetting state in effects.
- **Themes:** the colour names in `globals.css` map onto the shared `--dh-*` tokens by `@theme inline`; `dh-theme.js` sets `data-theme` (two states, system default, `dh-theme` cookie). Use token classes (`bg-base-800`, `text-text-secondary`, `text-caption`, …), not raw hex. Anything drawn on a shield uses `fill-on-shield`/`stroke-on-shield`.
- **Removing an image is not deleting a record.** `DELETE /record/{id}` keeps the record, so that action says "images" and skips rows with none. Only a devmode darkroom deletes records, with `POST /purge` or `POST /purge/{id}`; **Purge N records** renders only with `health.devmode`.
- **Purge all** renders only when `health.devmode`; `History.test.tsx` asserts the button is absent from the DOM otherwise. The mock answers 404 to `POST /purge` without `MOCK_DEVMODE`, as darkroom does.
- **Fixture content:** flat colour fields with a label and nothing else. Nothing sexual, violent or otherwise flagged goes in the repo, generated or not.
- **Git:** see Branches below and `.cursor/rules/git-workflow.mdc`. Run `make check` before a PR. Never force-push; never commit `.env`.

## Branches

`dev` is the default branch and the base for every PR. Cut feature branches from `origin/dev` and bring them up to date by merging `origin/dev`, never `main`. Never push work to `main` or open a PR against it, except the release PR from `dev`: `main` must never be ahead of `dev`, with one exception. A release fast-forwards `main` to a `dev` commit that passed CI (`git push origin origin/dev:main`), then tags it. If `main` is protected, the release is a reviewed PR from `dev` into `main`, and merging it leaves a merge commit on `main` alone. That merge commit is the one exception to the rule: it leaves `main` one commit ahead of `dev` with an identical tree. Leave it there and don't merge `main` back into `dev`. Anything else on `main` that `dev` lacks is a mistake (`git diff origin/dev origin/main` must be empty). Once `main` carries such a commit it can't be fast-forwarded, so later releases are PRs too.
